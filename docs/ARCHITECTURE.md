# System Architecture

## 1. Overview

Construction Safety Risk Predictor is an end-to-end MLOps project that
connects an agent-based construction safety simulation with a deployable
machine-learning inference service.

The system contains four major layers:

```text
Simulation
    |
    v
Data Generation
    |
    v
Machine Learning Pipeline
    |
    v
Production Inference
    |
    v
Web Interface
```

The complete production architecture is:

```text
Agent-Based Simulation
        |
        v
Synthetic Dataset
1,000,000 worker decisions
        |
        v
Simulation-Level Split
Train / Validation / Test
        |
        v
+-------------------------------+
| Machine Learning Training     |
|                               |
| Logistic Regression           |
| Random Forest                 |
| XGBoost                       |
+-------------------------------+
        |
        v
MLflow Experiment Tracking
        |
        v
Best Validation Model
        |
        v
Threshold Optimization
        |
        v

        |
        v

        |
        v

        |
        v

        |
        +--------------------+
        |                    |
        v                    v
Swagger / API          Streamlit UI
                           |
                           v
                   Streamlit Cloud
```

## 2. Design Goals

The architecture was designed around the following goals:

- reproducible synthetic data generation
- leakage-safe model evaluation
- comparison of multiple ML model families
- explicit experiment tracking
- production model serialization
- validated REST inference
- containerized deployment
- lightweight runtime monitoring
- continuous integration
- public demonstration through a web interface

The project intentionally separates:

```text
simulation logic
training logic
inference logic
presentation logic
```

This keeps the production system independent from the full simulation stack.

---

# 3. Source Simulation Layer

The project starts with the agent-based construction safety model.

The simulation models construction workers whose safety decisions depend on
behavioral and cognitive variables.

Important worker-state variables include:

```text
SA   - Situational Awareness
SK   - Safety Knowledge
SN   - Subjective Norm
BA   - Behavior Attitude
PBC  - Perceived Behavior Control
```

The model also uses Cumulative Prospect Theory parameters:

```text
reference_point
alpha
beta
lam
```

A derived intention variable is calculated as:

```text
intention = (SN + BA + PBC) / 3
```

The target variable is:

```text
behavior
```

where:

```text
1 = safe behavior
0 = unsafe behavior
```

---

# 4. Why the Simulation Is Part of the ML Architecture

The machine-learning model is not trained on an external static dataset.

Instead, training data is generated by executing the simulation repeatedly.

This creates the pipeline:

```text
Behavioral theory
      |
      v
Agent-based model
      |
      v
Synthetic worker decisions
      |
      v
Supervised ML surrogate
```

The ML model therefore learns to approximate the behavior of the source
simulation.

This is known as a surrogate-model approach.

# 5. Data Generation Architecture

Dataset generation is implemented in:

```text

```

The generator executes multiple independent simulation runs.

Configuration:

```text

100 workers per run
100 simulation days
```

The expected number of records is:

```text
100 × 100 × 100

```

Each row represents one worker decision at one simulated time step.

# 7. Identifier Isolation

The following columns are generated for traceability:

```text
run_id
seed
worker_id
```

They are deliberately excluded from training.

They identify simulation entities rather than worker safety characteristics.

Using them as predictive features could allow the model to learn
simulation-specific patterns instead of general behavioral relationships.

Therefore:

```text
Identifiers -> grouping and analysis
Features    -> machine learning
Target      -> prediction objective
```

---

# 8. Simulation-Level Data Split

A standard random row split would be inappropriate for this project.

Rows belonging to the same simulation run are correlated because they share:

- random seed
- simulated environment
- evolving worker states
- simulation history

If rows from one run appeared in both training and testing data, performance
could be artificially optimistic.

Therefore the project performs splitting at the simulation-run level.

Conceptually:

```text
Simulation runs 0 ... 79
        |
        v
Training set

Simulation runs 80 ... 89
        |
        v
Validation set

Simulation runs 90 ... 99
        |
        v
Test set
```

The exact split is performed by the training pipeline.

This creates approximately:

```text
800,000 training rows
100,000 validation rows
100,000 test rows
```

The key property is:

```text
No simulation run appears in more than one split.
```

---

# 9. Why Grouped Splitting Matters

Without simulation-level isolation:

```text
same simulation
    |
    +--> train
    |
    +--> test
```

could lead to information leakage.

The implemented architecture instead guarantees:

```text
training simulations
        !=
validation simulations
        !=
test simulations
```

This provides a more realistic estimate of how the surrogate performs on
previously unseen simulation runs.

# 10. Machine Learning Layer

Training is implemented in:

```text
src/train.py
```

Three model families are compared:

```text
Logistic Regression
Random Forest
XGBoost
```

They represent progressively more flexible learning approaches.

---

# 11. Logistic Regression

Logistic Regression is used as the baseline.

Its role is to answer:

```text
Can a simple linear decision boundary reproduce the simulation?
```

Advantages:

- fast training
- interpretable baseline
- low computational cost
- useful benchmark for more complex models

---

# 12. Random Forest

Random Forest introduces nonlinear interactions.

It can model relationships such as:

```text
high SA
AND
high SK
AND
specific PBC range
```

without manually defining interaction terms.

It also provides tree-based feature importance.

---

# 13. XGBoost

XGBoost is the most powerful model family tested in the project.

It uses gradient-boosted decision trees and can capture nonlinear
relationships in the simulation-generated data.

The final validation comparison selected:

```text
XGBoost
```

as the production model.

# 15. Metrics

The project tracks multiple classification metrics.

These include:

```text

```

Using several metrics is important because the classes are not perfectly

---

# 16. Why Macro F1 Is Used

The project uses Macro F1 as the main model-selection and threshold
optimization metric.

Macro F1 is calculated as:

```text
F1_safe + F1_unsafe
-------------------
         2
```

This gives equal importance to both classes.

Without this, a model could achieve relatively high overall accuracy by
favoring the majority class.

# 18. Why MLflow Is Used

Without experiment tracking, model development can become:

```text
train model
change parameters
train again
forget previous result
```

MLflow converts this into:

```text
Experiment
    |
    +--> Logistic Regression run
    |
    +--> Random Forest run
    |
    +--> XGBoost run
```

Each result becomes reproducible and inspectable.

# 19. Model Selection

Models are compared on validation simulations.

The selected model is:

```text
XGBoost
```

The validation Macro F1 score of the selected model is approximately:

```text
0.6126
```

The test set remains untouched during model selection.

This separation prevents test-set tuning.

---

# 20. Threshold Optimization

Binary classifiers normally use a probability threshold of:

```text
0.50
```

However, the default threshold is not always optimal.

The project evaluates different thresholds using validation data.

The selected threshold is:

```text
0.64
```

The production decision rule is:

```text
if P(safe) >= 0.64:
    predict SAFE
else:
    predict UNSAFE
```

---

# 21. Threshold Selection Architecture

The process is:

```text
Validation probabilities
        |
        v
Threshold sweep
0.05 ... 0.95
        |
        v
Calculate Macro F1
for each threshold
        |
        v
Select best threshold
        |
        v
0.64
```

Only validation data is used for threshold selection.

The final threshold is then applied once to the held-out test set.

# 22. Production Artifacts

Production inference uses the exact model that was evaluated.

# 50. Reproducibility

### Simulation seeds

Dataset generation records random seeds.

### Group identifiers

Rows retain simulation run information.

### Fixed feature schema

Production inference uses the same ordered feature list as training.

### MLflow

### Serialized model

The selected production model is versioned as an artifact.

### Docker

The API runs in a reproducible environment.

### CI

Automated tests execute after repository changes.

# 55. Architectural Limitations

The project also has deliberate limitations.

The data is synthetic.

The model has not been validated on real construction sites.

Monitoring is in-memory.

MLflow currently operates as a local experiment-tracking environment rather
than a persistent hosted tracking server.

The Render backend uses a free instance and can experience cold starts.

These limitations are documented rather than hidden.
